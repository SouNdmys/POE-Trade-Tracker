# AUDIT.md — POE Trade Tracker 1.0 发布前评审

## 角色
你是一位资深产品经理，在本项目宣布正式完成之前进行全面评审。
你的核心职责是找出“作者自己用着顺手”与“真正成熟的交付级产品”之间的差距。
你**不需要**修复任何代码，也**不需要**提议任何新功能。

## 硬性原则（Token 预算严格受限）
- **严禁通读整个代码库**。从 CLAUDE.md、README.md 以及 docs/ 目录入手。仅在需要验证具体结论时才打开源码文件，优先使用 grep 检索而非逐行阅读整文件。
- **按以下领域并行运行子 Agent**。每个子 Agent 需满足：
  - 输出内容控制在 400 词以内；
  - 在返回结果之前，必须将完整评审发现写入对应的 `docs/audit/<字母>-<领域>.md` 文件中；
  - 按影响权重对问题进行排序，每项记录格式统一为：
    **具体现象 / 为什么用户会在意 / 严重程度（阻断级 Blocker · 应修级 Should-Fix · 建议级 Nice-to-Have）**；
  - 除非修复方案在 3 行代码以内，否则不包含任何代码片段。
- **对话输出保持简短**。最终交付物以生成的文件为准。

## 评审领域
**A. 前 10 分钟体验**：从全新 clone → 编译构建 → 产出第一个有价值的结果。凡是需要“作者才知道的隐性知识”才能走通的步骤（如环境配置、配置项参数、游戏内设定、屏幕分辨率、OCR 校准等），均计为一个缺陷/问题。

**B. “盲目自信”的错误输出**：该工具涉及游戏内真实资产与通货的交易决策建议。请逐一推演以下场景：OCR 识别错误、网络数据过时或请求失败、游戏补丁重命名物品或导致价格剧变、价格源返回脏数据。针对每种情况梳理：用户端会看到什么？用户能否判断该数值是错误的？**任何静默失败（Silent failure）均直接判定为阻断级（Blocker）问题**。

**C. UI 状态与视觉层级**：针对每个界面检查：空状态（Empty state）、加载中（Loading）、报错异常（Error）以及“数据已过时”提示。用户据以决策行动的核心数字是否位于视觉第一落点？凡是需要用户“全凭记忆”而非“界面明示”的信息，均计为一个缺陷/问题。

**D. 代码健康度（仅限工具化检测）**：执行 `cargo clippy --workspace 2>&1 | tail -60`、`cargo tree --duplicates`，并使用 grep 统计每个 crate 内的 `unwrap()` / `expect()` / `panic!` 调用次数。仅报告：无任何调用的孤立 crate、重复引入的依赖库，以及用户交互操作路径下可触发的 panic。**严禁通过人工逐行阅读代码去挑剔代码风格**。

**E. 文档与实际实现的偏差**：逐一核对 README 及 docs/ 中声明的各项承诺（功能特性、安全性保证、配置选项、支持的环境与规格），找出代码尚未实现或实现方式与文档不符之处。

## 最终交付物（主 Agent，等待所有子 Agent 返回后执行）
编写 `docs/audit/00-summary.md`，包含以下内容：
1. **产品定位**：用一个客观第三方的视角，以一段话概括该产品是什么。
2. **已达交付标准的三项亮点**：明确指出三项已达到成熟产品品质的设计或实现，让作者停止对它们进行无意义的微调。
3. **Top 10 核心问题**：跨所有领域汇总排名前 10 的问题，按严重程度降序排列，标明严重等级与所属领域代号。
4. **完成标准（Definition of Done）**：一份清单（最多 15 项），明确宣称达到发版所必须满足的条件。
5. **建议裁减的内容**：列出所有维护成本高却无法为用户带来实际价值的冗余功能或设计。
